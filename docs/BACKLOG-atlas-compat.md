# Connect: Atlas compatibility backlog

Written 2026-10-28 from Atlas VTT's patch notes (0.2.0 to 0.10.2) against a quick search of Connect's code (0.6.2). Updated 2026-11-01 for Atlas 0.12.0 (see "Atlas 0.12" below).
Nothing here was run against a live Atlas. **Verify** means "check Connect's behaviour first; it may already be right".
Atlas versions are in brackets. Order is priority: P0 first, and inside a tier top to bottom.

## Done

- [x] **Atlas 0.12.0 audit (2026-11-01).** Read from the source diff of the tags 0.11.0 and 0.12.0, not run against a live 0.12. Nothing Connect's stock shim reads was removed or changed: the map view's store and `tabMetaStore`, `presentedScene` (`get`, `onChange`, `showElsewhere`), the settings service (`getLocalPlayerViewSettings` and the rest), the dice path (`rollDice`, `getDiceRules`, the event bus, the `dice-rolled` event), the rules path, the tile service (`open`, `overview`, `close`), the lighting controller (`playerSight` and the rest), the map file format (only `playerFrames` was added, and Connect ignores it) and the toolbar classes Connect injects into. Tabletop and Atlas Physical Dice read the same objects and are unaffected. The audit did not cover the generator's output shapes (`toLiquids`, `toWalls`).

- [x] **Tabletop's board for players: turned doors, daylight tint and stacked scenes (2026-11-02, not released).** `BoardDoor.hinge/side`, `BoardExtras.tint` and `BoardExtras.layers` are optional wire fields (an older player ignores them). A stacked scene goes as its floor, walls, doors, lights and props by asset id, in the first part only, at most 8 layers and 110 KB; its tokens, pins, notes and fog never go, and its fog does not hide anything of it (Connect reads only the presented scene through Atlas's views). Tabletop's setting **Show layers to Connect players** turns it off. Tests: `projectBoard.test.ts`, `boardSender.test.ts`. Not done: the GM's camera on a stacked scene is not converted to the presented scene's frame; players have no ruler to switch layers.
- [x] Atlas 0.10 levels: players get only the floor a view shows (0.6.2)
- [x] Dice rules per collection: default roll, critical rule, exploding (0.5.0)
- [x] Custom stat block templates, and Atlas's own card (0.4.0, 0.5.0)
- [x] Dynamic lighting read from Atlas 0.9.1 (0.6.0)
- [x] A stat block's Rollable setting kept online, rolls named after the label before the number (0.6.2)
- [x] Valued conditions, per-token resource visibility

## P0: what players see must match Atlas (leaks or wrong pictures)

- [x] **Token numbers (0.10.2).** Fixed 2026-10-28, not yet released. Connect now ports Atlas 0.10.2's rule (`K2e`): a token whose art two or more tokens of the scene share, hidden, fogged and off-map ones counted, shows its own stored `instanceNumber ?? 1`. Nothing is renumbered, and a bad stored number is cleaned to a whole number from 1 to 9999. Removed `instanceNumbers.ts` and the memo field. Tests: `instanceBadges.test.ts`. Verified by code and tests, not live.
- [x] **Hidden tokens give players no sight and no explored area (0.7.0).** Verified 2026-10-28 by code: Connect computes no sight at all. `LiveLighting.ts` and `stockLighting.ts` take Atlas's own `playerVisibility` (its player sight and token perception), so this is Atlas's rule, mirrored. Risk is only that the stock shim reads Atlas's private objects: retest on each Atlas release. Not tested live.
- [x] **Tokens and door icons under fog are hidden from players, with their names and rulers (0.7.0).** Verified 2026-10-28 by code and tests. Tokens: dropped with their name, statblock name and art (`unsentTokensLeak.test.ts` checks the whole scene JSON and the asset registry; `projectForPlayers.test.ts` covers fog and hidden tokens and initiative entries). Doors and walls: only the Tabletop board path sends them, and it checks fog (`projectBoard.test.ts`, door-under-fog case added). Rulers: Connect relays no GM rulers or drag paths to players (the only tool messages are dice, lasers, pings and players' own templates), so nothing to hide.
- [x] **A roll shows its token picture and name only when players can see that token (0.7.0).** Verified 2026-10-28 by code and tests. Connect names a statblock roll after its token only if that token is in what was last sent to players (a hidden or fogged one is not), else "GM"; the log entry has no picture field at all. The ability stays, which is Atlas's own rule (`PlayerDiceToasts`: a hidden token's roll "keeps its ability and result but not the token's name or portrait"). Tests: `diceHost.test.ts` (new case: no name, picture or token fields in anything sent, the ability kept), and the existing hidden and fogged cases.
- [x] **Measurements that start on an unseen token are hidden from players (0.7.0).** Verified 2026-10-28: not applicable. Connect's protocol carries no GM measurement. The only shapes it relays are templates players place themselves at free points (`map-template`), with no link to a token.
- [x] **Light and sight edge cases (0.10.0, 0.10.2).** Verified 2026-10-28 by code, no change needed. Connect computes none of it: it reads Atlas's own sight, perception and light reach through the stock shim, so Atlas's fixes (a token at a light's edge, magical darkness, one-way walls) come with Atlas. Checked against the 0.10.2 build: every member the shim reads still exists (`playerSight`, `sightIsCurrent`, `currentSight`, `ambientLight`, `lightReaches`, `playerFramePerception`, `getTokenRenderer`), and the sight object's shape and sense values (`all`, `regions`, `bright/dim/dark/magicalDark`, `as-bright`, `as-dim`, `reveals`, `lineOfSight`, `precise`) match what the shim validates. Not run live. Open: Tabletop's own 3D lighting is separate and not covered here. The sub-items below are the original list.
  - a token exactly at a light's edge is lit from both sides or neither
  - magical darkness, including a small light outshining it, giving the next token sight
  - one-way walls: no thick black line where they stop a light
- [x] **Grid alignment that turns or shifts the map (0.7.1; fixed for Atlas Online in 0.10.2).** Done in Connect 2026-10-28, committed locally, not released. Atlas keeps a map's alignment as `grid.mapStretch` (factors 1 to 1.5, a turn of at most 5 degrees) and, per level, `levelAlignments` (stretch, scale, offset). The world rect Connect already sends is the aligned image's box, so a pure stretch was already right. A turn or an offset left the image misplaced against the grid and tokens. Connect now reads the shown level's effective alignment in the stock shim (`mapAlignment`), ports Atlas's own rules (`mapPlacement.ts`: `Uf`, `Fan`, `CA`, `$4`, `oxe`, `xH`), and sends a six-number matrix as the optional `map.matrix`, only for a turned or shifted map. The 2D page draws it (`ViewSurface.imageMatrix`). Older pages ignore the field and draw as before. The web player page must be republished to get it. Tests: `mapPlacement.test.ts` checks the matrix against a copy of Atlas's `xH` at many points; projection, validation (a bad matrix is refused, a missing one is fine), the map layer and the shim snapshot are covered. Verified by code and tests, not live.
  - [x] **Tabletop's 3D player board and its own GM board.** Done 2026-10-29 in the Tabletop repo (uncommitted there, mixed with other work; built and installed in the vault). The player board takes its size from the world Connect sends (`map.width`/`height`, not the image's pixels, which a shrunk copy changes) and lays the image by `map.matrix` (a unit-square plane carried by the matrix; without one the image fills the world), and rebuilds when either changes. The GM board already laid the image by Atlas's `grid.mapStretch` (`mapStretch.ts`). Test: `sceneAdapter.test.ts`. Not checked live.

## P1: map and scene content

- [x] **Animated maps: WebM and MP4 as the background (0.10.0).** Done 2026-10-29 (committed locally, not released; not tried live in a browser). Players still get the still of the first frame as the map (works everywhere). Now the web page also plays the video: an MP4 or WebM up to 64 MB goes as an asset of its own (`map.video`, new mime types `video/mp4` and `video/webm`), requested last so it never holds up the still, tokens or handout; the page decodes it into a muted, looping `<video>` that the map layer draws every frame (the view keeps repainting while it plays, a paused one is restarted), the still showing until it is ready. Over 64 MB, or `.mov` and `.ogv`: still only, and the GM is told once. Cost to know: the video is sent to each player separately, like any asset. The Obsidian scene tab and Tabletop's 3D board keep the still (the tab's player does not ask for the video). Tests: `animatedMapVideo.test.ts`. The web page must be republished; an older page ignores `map.video`.
- [x] **Generated dungeons' water, lava and acid (0.10.0), still.** Done 2026-10-29 (committed locally, not released; the animation is not done). Atlas's `objects.liquids` (kind, outline, holes, colours) now go to players inside `map.liquids`, drawn over the map image and under the grid and fog: the outline filled in its surface colour (even-odd, so holes are cut out) with a thin glint along its edge. Bounded (64 liquids, 2048 points an outline, 16 holes, 20 000 points in all), colours `#rrggbb` or the kind's own palette, wire-validated, absent without any, older pages ignore it. Not done: Atlas's flow and shimmer (a shader), and the Tabletop 3D board does not draw them. Tests: `liquids.test.ts`. The web page must be republished.
- [x] **Replace map image (0.10.0).** Verified 2026-10-28 by Atlas's code and a test; no change needed. Atlas swaps the scene's map (or a level's own image) for another version of it, the aspect having to match, and the grid, walls and lights stay. Connect follows the new image through the background path like any other change, so players get the new map; a video becomes a still (see Animated maps), and a larger export falls under Huge maps. Test: `stockAtlas.test.ts` (the scene's own and a level's image). Not run live.
- [x] **Huge maps, up to 144 megapixels, and SVG maps (0.7.0).** Done 2026-10-28 (committed locally, not released), with one part left open. SVG: players decode it through an `<img>`, which draws it sharp at any zoom; nothing to change. Huge: any raster map over the 64 MB limit (a full-quality 144 MP PNG) was refused, so players got a blank map. Now it is sent as a WebP copy cut to 8192 pixels on its longer side (smaller still if the copy is over three quarters of the limit), decoded at that size so the whole image is never held in memory, made once per file change, with one notice to the GM. A vector or a model over the limit is still refused. Tests: `hugeMaps.test.ts`. **Open:** a map under 64 MB but of many megapixels (a 144 MP JPEG of 30 MB) is still sent whole, and a phone may not decode it. Cutting by pixels too would change what players get for maps that work today, so it needs the user's call. Not run live: the cut-down uses `createImageBitmap` with a size and an `OffscreenCanvas` in the GM's window.
- [x] **Mosaic Canvas: maps of up to 1,000 megapixels, files of any size (0.11.0).** Done 2026-10-31 (not committed, not released; the web page needs no republish, the protocol is unchanged; never run against a live Atlas 0.11). The GM side now makes the smaller copy players get from Atlas's own tile service (found through an open map view: `renderer.getMapImage().deps.service`: `open`, `overview`, `close`) instead of reading the file, so a 200 MB or 2 GB map works; without the service (an older Atlas, no map view open) it reads and cuts the file as before. It also closes the open item of *Huge maps* below: a file under 64 MB (8 MB and up is measured, once per file change) with more than 144 megapixels, what Atlas held before 0.11, is sent as the copy too; maps of up to 144 megapixels go as they always did. Tests: `atlasMosaic.test.ts`. Players' cell numbers, fog and grid already degrade on big grids (`MAX_NUMBERED_CELLS`, `MAX_FOG_CELLS`, `GridLimits`); liquids carry only the fields Connect knows, so 0.11's new `course`, `openEdges` and `crayon` art are ignored.
- [x] **Level switching for players (0.10.0).** Fixed 2026-10-28 (committed locally, not released), and it was a privacy bug of 0.6.2's own level work, not only a missing feature. Atlas shows players the level its presented scene names (`presentedScene.levelId`, set by "Show this level on the player view"), the first level where none is named, and holds the last picture while the GM looks at another level (`N4e`). Connect sent the floor the GM was browsing, so a GM exploring floor 2 would have shown it. Now the shim gives the presented tab's snapshot no live tab (`tabId` null) while the GM's level differs from the players', so Connect's scene-tab layer sends nothing of that floor and players keep the last picture; naming a level on the player view makes it live again, as a new presentation. The presentation's `held` flag follows the same rule. Players cannot switch floors themselves: neither Atlas nor Atlas Online lets them. Tests: `stockAtlas.test.ts`, `stockLevels.test.ts`. Open: a scene held from the start (the GM presents while on a floor other than the one shown) has no live picture until the GM returns to it, as in Atlas's own online play; and tabs that are not the presented one (split groups) have no presented level, so they follow their view's floor.
- [x] **Per-scene distance per cell (0.6.0), cell numbering A1, B1 (0.6.0), cone shapes follow the game system (0.5.0).** Fixed 2026-10-29 (committed locally, not released). The per-scene distance (`unitDistanceOverride`) and the cell numbering formats (including A1, B1) were already read the way Atlas 0.10.2 reads them. The gap: the stock shim never read the collection's measurement rules (`gridDefaults`: unit, distance per square, metric or range bands, diagonal rule, range bands, cone angle), so `rules.forMap` gave none and players' rulers fell back to the map's own older grid fields. For a normal collection that meant range-band words instead of "30 ft", and 90 degree cones where the game system says 53.13. The shim now reads and validates the collection's `gridDefaults` (units, a positive distance, mode, diagonal rule, at most twelve range bands, a cone angle above 0 and up to 360) and builds the measurement from them, as Atlas does; what it cannot read it leaves unset. Tests: `stockRules.test.ts`. Open: Atlas also falls back to the game-system preset's cone angle when the collection sets none; the presets live in Atlas's code, out of reach, so that case reads 90 (collections made from a preset copy the angle into `gridDefaults`, so it rarely arises). `difficultTerrain` is not sent. Not run live.
- [x] **Tokens glide to their place (0.7.0).** Verified 2026-10-29 against the 0.10.2 build; no change needed. Connect's `tokenGlides.ts` already ports Atlas's glide: the same step (`exp(-elapsed / 50 ms)`, arrived within 0.05 px), a dragged token at the pointer, and, on a lit scene, only the player's own tokens gliding (Atlas's `mayGlide`).

## P1: stat blocks

- [ ] **Built-in templates (0.8.0).** 5e 2014 and 2024, Cairn, Draw Steel, Fate, generic creature, NPC and hazard. Connect can't read built-ins, so its text fallback treats them as 5e. Atlas's card is correct. Options: carry the built-in definitions into Connect, or ask Atlas for them.
- [ ] **`@` references in templates (0.9.0, 0.9.1).** `1d8 + @str.mod`, and references by label (`@str`). Resolved on Atlas's card, not in the text fallback.
- [ ] **Counters, tracked numbers, recovery actions (short and long rest), boxed numbers and gauges (0.9.0).** The card shows them; the text fallback shows the raw value.
- [x] **Tracked values written like `15 (natural armor)` (0.9.1), and `0` showing on tokens (0.8.0).** Fixed 2026-10-29 for the `0` (committed locally, not released). Atlas draws a static resource from a maximum of 0 up and any other from above 0 (`hD`); the shared rule Connect used asked every value for a maximum above 0, so an AC of 0 never reached players. Connect now has Atlas 0.10.2's rule (`visibleResources.ts`, used for the token bars and for the GM's per-token choices). Tests: `visibleResources.test.ts`. The note text `15 (natural armor)` is read by Atlas's own sync into the token's numbers, and Connect sends what the token holds, so there is nothing to do here; not checked live.
- [x] **Several tokens sharing one statblock (0.8.0).** Verified 2026-10-29 by code, not live: a token's sheet is keyed by the token (`TokenSheet.tokenId`) with that token's own resource values, and the sheet is built from its statblock note, so tokens sharing a note get their own HP and numbers.

## P2: dice

- [x] **Foundry and Roll20 notation (0.8.0).** Done 2026-10-29 (committed locally, not released). Fate dice (`dF`) are logged and listed (earlier the same day). The text-sheet fallback now detects dice as Atlas 0.10.2's own link detector does, ported from its grammar: rerolls (`2d6r<2`), success counts (`6d10>=8`, `cs`, `cf`), `d%`, Fate dice, explosions (`!`, `!!`, `xo`), keep and drop (`kh`, `dl`), `[label]` tags, the operators `+ - * / ×`, a run of bonuses as one roll (`+4+1`, as Atlas 0.9.1 does), a roll that must open with a sign or hold at least one die, no link beside an `@` reference, and the whole-text fallback. The formula sent is Atlas's own form (`N_`). The existing expectations (prose with `5-6`, `1–3`, `2d6!`, `x2d6`) all still hold. Decision made: I ported Atlas's expression grammar and its start and end rules but not its full formula parser, so a text the grammar accepts and Atlas's parser would refuse is linked here and refused by Atlas when rolled, which is logged for the GM. A die's `label` is still not carried to the log. Tests: `sheets.test.ts`. The web page must be republished.
- [x] **Dropped and rerolled dice struck through (0.8.0).** Fixed 2026-10-29 (committed locally, not released). The dice card struck through dropped dice, but the log did not, and `rerolled`, `success` and `failure` (Atlas 0.10.2's six marks on a rolled die, as its own validator lists them) were not carried at all, so a rerolled die looked like part of the sum. Connect now carries all of them through the wire check, the log model and both views (log and card), struck through when dropped or rerolled, coloured for a success or failure, and not also coloured as the highest face. Older pages ignore the new marks. Tests: `toolMessages.test.ts`, `diceLogModel.test.ts`, `diceLogView.test.ts`. The web page must be republished to show them.
- [x] **Players roll with advantage or disadvantage (0.9.1).** Done 2026-10-29 (committed locally, not released), with a design decision of mine. The gesture Atlas Online uses (right-click or long-press on a die) is in its hosted client, which is not in the vault, and in the client that is, those gestures take a die out of the tray, as Connect's do. So the player's tray now has an explicit Normal, Advantage and Disadvantage choice, like Atlas's own GM tray. It applies to the roll it can apply to, one d20 and nothing else in the tray (the roll a d20 system rolls twice and keeps one of); for any other roll it is off and the roll goes as it is. The choice travels as an optional `advantage` on the `dice-roll` message (a side that is neither is refused; an older GM ignores it), and the GM rolls it as it rolls a sheet roll's side: through Atlas's own request where the stock shim takes it, else as `2d20kh1` or `2d20kl1`. A roll with a side is the GM's to roll, not thrown on the 3D board, since the board throws no second die to keep or drop. The tray opens empty and normal each time. Tests: `diceTray.test.ts`, `diceTrayView.test.ts`, `diceFormulaFit.test.ts`, `protocol.test.ts`. Open: the tray of the remote scene tab (a scene hosted by Atlas itself) has none. The web page must be republished.
- [x] **Public dice rolls toggle (0.7.0).** Fixed 2026-10-29 (committed locally, not released), and it was a privacy leak: **the GM's secret rolls reached every online player.** In Atlas the GM's own rolls are private by default (`localPlayerView.showDiceRolls` is off) and the dice tray's "Show my rolls to players" switches them on; Atlas's own online play reads the same setting. Connect sent every roll Atlas logged, so a roll the GM made behind the screen appeared in players' log and card as "GM". Now Connect asks at each roll whether the GM shares: the stock shim reports `showDiceRolls` (an addition to the API's four player-view rules), the dice host holds back a GM roll when it is off, and a roll made for a player is always the table's. A GM roll made while it was off is not in the replay a later player gets, and turning the setting off hides the next ones again. Where an Atlas reports no such rule (the real extension API today) rolls are shared as before. **This changes what GMs see happen:** with Atlas's default (off) a GM's rolls no longer appear to players until the GM turns on "Show my rolls to players" in the dice tray. Tests: `diceHost.test.ts`, `stockAtlas.test.ts`. Not run live.
- [x] **Players' reroll notation on Tabletop's 3D board (`2d6r<2`, `ro`, `rr`; Atlas 0.8).** Done 2026-10-29 (not committed, not released) as a request from the Tabletop side, **inert until Tabletop sets `PlayerBoardHandle.rerolls = true`**. Before this, `2d6r<2` was not thrown plain: the vendored `parseFormula` (API 1.18.0) cannot read a reroll, so the roll went to the GM's Atlas, which rolls it correctly and strikes the die through. Now `diceRerolls.ts` ports Atlas's term grammar (`YCn`, `JCn`, `ife`, `UCn`) and is the one reader both sides use: the player's `sheetThrow` asks a board that says it `rerolls` for the request with `reroll` (per kind: op, value, limit; `r` and `ro` 1, `rr` 10, a bare `r` rerolls ones), and the GM re-derives the rule from **its own copy** of the sheet roll (`SheetHost.rollFormula`), never from the message. Anything unsure stays the GM's roll: a rule every face meets, one kind of die with different or partial rules, a side (advantage), the collection exploding that kind, explosions/keeps/success counts/Fate/labels in the term. The GM refuses a die marked rerolled that the rule would not reroll, a standing die that meets the rule without its rerolls (not when the roll holds 20 dice), more rerolls than `limit` per die, a roll with other dice than the sheet roll throws, and any rerolled die in a tray roll or a kind with no rule. `rerolled` is on the wire (never with `dropped`), carried onto Atlas's roll and on to the log; total, critical result and the thrown formula skip it, and it earns no explosion. Tests: `physicalRerolls.test.ts`. **Open:** the logged formula reads `2d6+3`, not `2d6r<2+3`; keeps (`4d6kh3`) and success counts (`6d10>=8`) are still the GM's roll (they fail the parse, so nothing is thrown wrongly), and passing them through would need their own GM-side validation. Not run against a real Tabletop.
- [ ] **Dice Lab sets (0.8.0).** Own colours and names, and advantage and disadvantage edge rules (keep best, add or subtract a number, add or subtract a die). Connect's online tray doesn't read them. Tabletop does as of 2026-10-28; reuse its `rollRules.ts`.
- [x] **Invalid or oversized formulas rejected with a clear message (0.7.0).** Looked at 2026-10-29: little left to do. A player cannot send a free formula: the tray sends dice counts (at most 20 dice, a bounded modifier) and a sheet roll is asked for by place, re-derived by the GM's own copy, so an invalid or oversized formula cannot be formed from a page. A roll the session cannot take already tells the player why (`rollRefusal`); one Atlas itself refuses is logged for the GM and the player is told nothing. Open, minor: telling the player when Atlas refuses a roll.

## P2: initiative and turns

- [ ] **Audit Connect's initiative against Atlas (0.5.0 to 0.9.0).** Started 2026-10-29, against the 0.10.2 build's player list (`wPt`, `mPt`, `wae`, `lPs` in `main.js`), not the patch notes. Already right: cards (a combatant's number is its card), sitting out, delayed combatants lose the turn, two sides with the first side and the side to act, hidden tokens' entries dropped. **Fixed** (not committed, not released; the web page must be republished): a delayed combatant is now listed apart under "Delayed" after the order, as Atlas does (`entry.delayed`, turn order only), and a number not rolled yet (`awaitingInitiative` at 0, or a card not dealt) shows a dash instead of 0 (`entry.awaiting`); both are optional wire fields an older page ignores, and the Obsidian scene tab gets them too. Tests: `initiativeSides.test.ts`, `initiativeView.test.ts`. Not run live. **Open, found by the audit:**
  - 2026-11-01 (against Atlas 0.12.0's online combatant, `protocol/initiative.ts`): Atlas's card also carries the token's **conditions** and **instance number**, and the list has `bannerOff` and a spotlight flash on the token when its turn starts. Done now: Connect's cards show the conditions (up to four chips, then "+n") and the `#n` number, drawn from the token Connect already sends (no wire change; the page and the Obsidian tab share the view). Still open: Atlas's turn banner and its `bannerOff` switch, the token flash, and the HP numbers on the card (Connect shows only the bar). Tests: `initiativeView.test.ts`.
  - [x] **More than two sides, and sides that roll for the order each round (0.10).** Done 2026-10-29 (not committed, not released; the web page must be republished). Done for support, whether or not a given table uses it. Atlas lets a collection name up to eight sides and roll for the order every round (sides with an equal roll act together); Connect knew only `players` and `opponents`, so a named side's combatants were misfiled, no side showed the turn, "Your turn" and the move-on-your-turn hold could be wrong (with only a named side acting, the old single `active` is undefined and **every token was held**), and rolls never reached players. Now: the shim reads the collection's `sides`; `initiativeSides.ts` ports Atlas's `pAn`, `Ly`, `C1t`, `uk`, `gG` and `Y2e` and is tested against transcribed copies of them (plus a `__proto__` side id); the projection sends Atlas Online's own shape, `initiative.sideList` (id, name, roll, turn, in the order the sides act) and `sideId` on an entry of a named side. **Older pages keep working:** `side`, `sides.first` and `sides.active` still read only `players` or `opponents` (a named side reads `opponents`, `active` is the first built-in side acting, none where only named sides do), and the validator accepts the new fields as optional. The page (and the Obsidian tab) group by the list, show "name, rolled N" and mark every acting side; the text summary does too; `turnOf`, `nextTurnOf` and `heldOffTurn` work from the set of acting sides (the next group is the next row with its equal rolls; after the last row, where sides roll, the next round is unknown and no "next" is claimed); the Obsidian tab hands Atlas's own list its `order`, the round's `rolls` and the named side of each token (only when a named side or a roll needs it, so a plain fight converts as before). **Privacy choice (mine, on the safe side):** a side is named only if a combatant of it is in the list players receive, so the name of a side holding only hidden combatants is not sent (Atlas Online sends every side's name). Tests: `initiativeNamedSides.test.ts`, `stockRules.test.ts`. Not run live; the shim reads the fight's `order`, `roll` and `rolls` from Atlas's private state (the API's type lacks them), so retest on each Atlas release. **Open:** Tabletop's own initiative panel (`initiativePanel.ts`, its repo) is not changed and still knows two sides.
  - **Off-map combatants (0.9).** Checked 2026-10-29 in the 0.10.2 build: both Atlas's local player list and its online one list a combatant if its token exists and is not hidden (`gPt`, over the raw token record), so one kept beside the map (`offMap`) **is listed to players** with its name, number and HP bar, and its portrait. Connect drops it: off-map tokens are filtered out of the sent tokens (`onMapTokens`), and an entry is listed only if its token was sent. So players of Connect never see reinforcements the GM added to the fight without placing them. **Decided 2026-10-29 by the user: keep hiding them** (the safe side of the difference; a GM can already hide a token in Atlas). No change planned. Mirroring it would send the entry without a portrait (the portrait comes from a sent token, and an off-map token must not be drawn on the map), or a new wire field for its art. Also seen: Atlas's list does not check fog for entries, only hidden; Connect also drops fogged ones, which is stricter and stays.
  - [x] **Defeated combatants.** Done 2026-10-29 (not committed, not released; the web page must be republished).
